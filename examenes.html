P1. Filtro convolucional en CUDA (5 pts)

Bloque 1

Filtro 3×3 sobre una imagen en blanco y negro de \(2^{13}\times2^{13}\) píxeles (1 byte por píxel). Un hilo por píxel; cada hilo necesita sus 8 vecinos. GPU NVIDIA H100: \(2^{10}\) hilos por bloque, hasta \(2^{31}\) bloques, 100 KB de shared memory por SM (no se comparte entre bloques).

1.1 Si cada bloque recibe 16×16 píxeles, ¿alcanzan los bloques? (1 pt)

Resolución oficial

Bloques necesarios \(=2^{26}/2^8=2^{18}\). Sí alcanzan (para una imagen; el solucionario agrega que para dos no alcanzarían, aunque \(2\cdot2^{18}\) sigue siendo mucho menor que \(2^{31}\)).

Cómo resolverlo
  1. Píxeles totales: \(2^{13}\cdot2^{13}=2^{26}\).
  2. Píxeles por bloque: \(16\cdot16=2^8\).
  3. Divide: \(2^{18}=262\,144\) bloques y compáralo con el máximo \(2^{31}\).

Trabaja en potencias de 2; las divisiones se vuelven restas de exponentes.

1.2 ¿La forma del bloque (cuadrado vs rectangular) afecta el desempeño? Considere el halo. (1.5 pts)

Resolución oficial

Un bloque 16×16 tiene un halo de 64 píxeles; uno rectangular (32×8 o 64×1) tiene mayor perímetro y ocupa más memoria. Bloques muy anchos también pueden afectar el acceso a memoria global: CUDA es eficiente cuando los 32 hilos de un warp acceden a direcciones contiguas (coalescencia).

Cómo resolverlo

Compara perímetros para el mismo área (256 píxeles): 16×16 → \(4\cdot16=64\); 32×8 → \(2(32+8)=80\); 64×1 → \(2(64+1)=130\). El halo es proporcional al perímetro, así que el cuadrado minimiza memoria y lecturas redundantes. Cierra mencionando coalescencia y warps de 32.

1.3 ¿Alcanza la shared memory para 16×16? ¿Se pueden usar bloques de 256×256? (1.5 pts)

Resolución oficial

16×16: \(4\cdot16+16\cdot16=320\) B < 100 KB. 256×256: \(4\cdot256+256\cdot256=66\,560\) B < 100 KB, también cabe; 512×512 ya no.

Cómo resolverlo
  1. Memoria del bloque = tile \(B^2\) + halo \(\approx4B\) (1 byte por píxel).
  2. Compara con 100 KB = 102 400 B.
  3. 512×512: \(262\,144+2048\) B > 100 KB.

Comentario que suma: 256×256 píxeles cabe en memoria, pero un bloque solo puede tener 1024 hilos, así que cada hilo tendría que procesar 64 píxeles.

1.4 Con \(10^{-7}\) s por píxel, ¿cuánto tarda un millón de convoluciones? ¿Y en secuencial? (1 pt)

Resolución oficial

\(t_p=10^{-7}\cdot10^6=0.1\) s (para una imagen). \(t_s=0.1\cdot2^{18}\cdot2^8=6.71\cdot10^6\) s ≈ 78 días.

Cómo resolverlo

En paralelo todos los píxeles se procesan a la vez, así que el tiempo es el de un hilo: \(10^6\) convoluciones × \(10^{-7}\) s. En secuencial se multiplica por el número de píxeles (\(2^{26}\approx6.7\cdot10^7\)). Convierte a días dividiendo entre 86 400.

P2. Árbol 2-3 (5 pts)

Bloque 2

Un árbol 2-3 tiene nodos internos con 2 o 3 hijos, todas las hojas a la misma distancia de la raíz y hojas ordenadas.

2.1 PRAM y span para buscar un elemento \(b\). (1 pt)

Resolución oficial
funcion postorden(i)
  if i == null: return
  else if i tiene 2 hijos:
      postorden(left[i]) || postorden(right[i]); sync
      if i == b: return True
  else if i tiene 3 hijos:
      postorden(left[i]) || postorden(mid[i]) || postorden(right[i]); sync
      if i == b: return True
  else return False

Span \(O(\log n)\) por la recursión. Alternativa: búsqueda binaria paralela \(O(\log n/\log p)\).

Cómo resolverlo

Lanza en paralelo la búsqueda en cada hijo (||) y sincroniza. La profundidad de la recursión es la altura del árbol, que en un 2-3 es \(\Theta(\log n)\) (entre \(\log_3 n\) y \(\log_2 n\)). Ese es el span. El trabajo es \(O(n)\) porque se visita todo.

2.2 PRAM y span para insertar un elemento \(b\). (0.5 pts)

Resolución oficial
for i < nh pardo
  1. if a_i = b: return True            // ya existe
  2. if a_i < b < a_{i+1}:
       b es el siguiente hijo de v, luego de a_i
       if v tenía 3 hijos (ahora 4):
          insertar en el padre w un hijo v1 después de v
          repartir los 4 hijos entre v y v1
          repetir recursivamente para w
     return True

Span: (1) \(O(1)\), (2) \(O(\log n)\) por la recursión hacia la raíz.

Cómo resolverlo

Ubicar la posición se hace comparando en paralelo contra todas las hojas (\(O(1)\)). Lo costoso es mantener la estructura: si un nodo queda con 4 hijos se parte en dos y eso puede propagarse hasta la raíz, una vez por nivel: \(O(\log n)\).

2.3 PRAM y span para insertar una secuencia \(b_0,\dots,b_{k-1}\). (2 pts)

Resolución oficial

Un bucle secuencial for i < k que envuelve el PRAM de 2.2. Span \(O(k\log n)\).

Cómo resolverlo

Cada inserción puede reestructurar el árbol, así que la siguiente depende del árbol actualizado: las \(k\) inserciones van en secuencia, cada una con span \(O(\log n)\). Si se pide optimizar, se puede mencionar insertar en paralelo elementos que caen en subárboles distintos.

2.4 Expresión de \(T(n,p)\) en cada caso. (1.5 pts)

Resolución oficial

Caso 1: \(O(\log n/p)\). Caso 2: \(O(\log n/p+\log n)\). Caso 3: \(O(k\log n/p+k\log n)\).

Cómo resolverlo

Aplica Brent \(T_p=W/p+T_\infty\) con el trabajo y span de cada caso. Justifica qué tomaste como trabajo; el solucionario usa \(W=\log n\) por inserción. Si tomas la búsqueda post-orden completa, \(W=n\) y \(T_p=n/p+\log n\), y también es defendible si lo argumentas.

P3. OpenMP: máximo de un arreglo (5 pts)

Bloque 3
double A[N]; double maximo = -1;
for (int i=0; i<N; i++) A[i] = rand()%100/1000.0;
double local_max;
#pragma omp parallel for
for (int i=0; i<N; i++) {
  if (A[i] > local_max) {
    #pragma omp atomic
    local_max = A[i];
  }
}
printf("Maximo: %f\n", local_max);

3.1 Encuentre dos errores. (1 pt)

Resolución oficial

(1) if (A[i] > local_max) local_max = A[i]; no es atómico en conjunto: atomic protege solo la escritura, no la condición. Es una condición de carrera read-check-update; atomic solo vale para operaciones simples como += o ++. (2) local_max no está inicializada.

Cómo resolverlo

Busca tres cosas en cualquier código OMP: variables compartidas modificadas sin protección, directivas usadas fuera de su alcance (atomic sobre un bloque compuesto) y variables sin inicializar. Explica el escenario: dos hilos pasan el if con el mismo valor viejo y el que escribe último puede dejar un valor menor.

3.2 Proponga una forma alternativa de paralelizar. Explique cómo corrige los errores. (2 pts)

Resolución oficial
double maximo = -1e9;
#pragma omp parallel
{
  double local_max = -1e9;
  #pragma omp for
  for (int i = 0; i < N; i++)
    if (A[i] > local_max) local_max = A[i];
  #pragma omp critical
  { if (local_max > maximo) maximo = local_max; }
}

O, mucho más eficiente, #pragma omp parallel for reduction(max:maximo).

Nota: en el solucionario el cuerpo del bucle con reduction aparece como maximo = A[i];, que es incorrecto. Debe ser if (A[i] > maximo) maximo = A[i];.

Cómo resolverlo

Patrón general: cada hilo calcula un resultado privado sin sincronización y solo al final combina en una sección crítica (\(p\) entradas a critical en vez de \(N\)). La forma idiomática es reduction(max:var): OpenMP crea las copias privadas, las inicializa con el neutro del máximo y las combina.

3.3 Versión con tasks. ¿Es más eficiente? (2 pts)

Resolución oficial
#pragma omp parallel
#pragma omp single
for (int i = 0; i < N; i++) {
  #pragma omp task firstprivate(i)
  {
    #pragma omp critical
    { if (A[i] > maximo) maximo = A[i]; }
  }
}

Otra versión: cada task escribe maximos_locales[i] y se reduce secuencialmente al final.

Cómo resolverlo

Estructura obligada: parallel + single (un hilo crea las tareas) + task firstprivate(i). Responde la comparación: una task por elemento con critical es menos eficiente que reduction, porque crear \(N\) tareas cuesta y critical serializa. Mejora: tareas por bloques de elementos con máximos locales.

P4. Topologías en Quicksort (5 pts)

Bloque 3

Quicksort paralelo de \(n\) elementos en \(p\) procesos. Comunicación: malla 2D \(\sqrt p\times\sqrt p\): \(T_{comm}=O(\alpha\sqrt p+\beta\frac{n}{\sqrt p})\); hipercubo de dimensión \(\log p\): \(T_{comm}=O(\alpha\log p+\beta\frac{n}{p\log p})\).

4.1 Complejidad del tiempo paralelo en cada caso. (1 pt)

Resolución oficial

\(T^{malla}=O(\frac{n\log n}{p}+\alpha\sqrt p+\beta\frac{n}{\sqrt p})\); \(T^{hiper}=O(\frac{n\log n}{p}+\alpha\log p+\beta\frac{n}{p\log p})\).

Cómo resolverlo

\(T_p=T_{comp}+T_{comm}\). El cómputo es el ordenamiento local repartido: \(T_s/p=n\log n/p\). Suma el costo de comunicación de cada topología.

4.2 Speedup y función de overhead. (1 pt)

Resolución oficial

\(S=\dfrac{n\log n}{T_p}\) en cada caso. \(T_0^{malla}=\alpha p\sqrt p+\beta n\sqrt p\); \(T_0^{hiper}=\alpha p\log p+\beta\frac{n}{\log p}\).

Cómo resolverlo

\(T_0=pT_p-W\): multiplica cada término de comunicación por \(p\). Por ejemplo \(p\cdot\beta\frac{n}{\sqrt p}=\beta n\sqrt p\).

4.3 Condición de escalabilidad para \(E=0.7\) y \(E=0.8\). (1.5 pts)

Resolución oficial

\(W=\frac{E}{1-E}T_0\). Malla: término dominante \(n\log n=\frac{E}{1-E}\alpha p^{3/2}\). Hipercubo: \(n\log n=\frac{E}{1-E}\alpha p\log p\) (el solucionario escribe \(\beta\), pero el término \(p\log p\) viene de \(\alpha\)). El hipercubo es más escalable.

Cómo resolverlo
  1. \(K=E/(1-E)\): \(E=0.7\to K=2.33\); \(E=0.8\to K=4\).
  2. Iguala \(n\log n=K\cdot\)(cada término de \(T_0\)).
  3. Malla: el término \(\alpha p^{3/2}\) obliga a crecer más que el de \(\beta\) (que da \(\log n\propto\sqrt p\)).
  4. Compara \(p^{3/2}\) contra \(p\log p\): crece más lento el hipercubo.

Subir \(E\) solo cambia la constante \(K\), no la forma de la relación.

4.4 Con \(n=10^6\), \(p=64\), \(\alpha=10^{-5}\), \(\beta=10^{-9}\): ¿cuántos procesos para un arreglo 10 veces mayor con \(E=0.8\)? (1.5 pts)

Resolución oficial

Malla: \(\frac{n_1\log n_1}{n_2\log n_2}=\frac{p_1^{3/2}}{p_2^{3/2}}\Rightarrow p_2\approx329\). Hipercubo: \(p_2\approx500\). Es redundante con 4.3; el factor \(E/(1-E)\) sirve para determinar la relación experimentalmente.

Cómo resolverlo
  1. Divide la relación de isoeficiencia del caso 2 entre la del caso 1: \(K\) y \(\alpha\) se cancelan.
  2. \(\frac{n_2\log n_2}{n_1\log n_1}=\frac{10^7\cdot7}{10^6\cdot6}=11.67\).
  3. Malla: \(p_2=64\cdot11.67^{2/3}=64\cdot5.14\approx329\).
  4. Hipercubo: \(p_2\log_2p_2=64\cdot6\cdot11.67=4480\); probando, \(500\cdot\log_2500\approx500\cdot8.97\approx4483\Rightarrow p_2\approx500\).

El hipercubo admite más procesos para el mismo crecimiento del problema: confirma que es más escalable.

P1. Value at Risk en GPU (6 pts)

Bloque 1

Un modelo VaR calcula \(N\) escenarios con \(M\) activos cada uno. Kernel por escenario: for j<M: dV += weights[p][j]*shocks[i][j]; (2 FLOP por iteración). \(N=2^8\) escenarios. H100: \(2^{10}\) hilos por bloque, hasta \(2^{31}\) bloques.

1.1 ¿Cuántos modelos se pueden simular si cada hilo resuelve un escenario? (1 pt)

Resolución oficial

\(2^{31}\cdot2^{10}/2^8=2^{33}\) modelos.

Cómo resolverlo

Hilos totales \(2^{41}\); cada modelo consume \(2^8\) hilos (uno por escenario). Modelos \(=2^{41}/2^8\).

1.2 Con \(M=2^8\) activos y \(10^{-8}\) s por suma/producto: tiempo paralelo y secuencial del total. (1 pt)

Resolución oficial

\(t_p=2\cdot10^{-8}\cdot2^8=5.12\cdot10^{-6}\) s. \(t_s=5.12\cdot10^{-6}\cdot2^{41}=11.25\cdot10^6\) s ≈ 130 días.

Cómo resolverlo

Un hilo hace \(M\) iteraciones de 2 FLOP: \(2M\) FLOP × \(10^{-8}\) s. Todos los hilos trabajan simultáneamente, así que \(t_p\) es el tiempo de uno. Secuencial: los \(2^{41}\) escenarios uno tras otro.

1.3 Speedup, eficiencia y FLOP/s. ¿Por qué el speedup es proporcional a los FLOP/s? (2 pts)

Resolución oficial

\(S=11.25\cdot10^6/5.12\cdot10^{-6}=2.2\cdot10^{12}\); \(E=2.2\cdot10^{12}/2^{41}=1\); FLOP/s \(=2\cdot2^8\cdot2^{41}/5.12\cdot10^{-6}=2.19\cdot10^{18}\) ≈ 220 EFLOP/s. Son proporcionales porque ambos tienen en el numerador cantidades proporcionales (FLOP totales y tiempo secuencial) divididas entre el tiempo paralelo.

Cómo resolverlo

\(S\) sale igual al número de hilos (\(2^{41}\)), así que \(E=1\). FLOP totales \(=2M\cdot\#\text{hilos}\), divididos entre \(t_p\). Para la justificación escribe \(t_s=\text{FLOP}\cdot t_{op}\Rightarrow S=\text{FLOP/s}\cdot t_{op}\).

1.4 Si los escenarios de un modelo deben compartir memoria (mismo bloque de \(2^{10}\) hilos): ¿cuántos modelos? Recalcule \(t_p\), \(S\), \(E\). (2 pts)

Resolución oficial

Un modelo por bloque: \(2^{31}\) modelos. \(t_s=5.12\cdot10^{-6}\cdot2^{31}=1.1\cdot10^4\) s, \(S=2.2\cdot10^9\), \(E=2.2\cdot10^9/2^{39}=0.004\). Speedup y eficiencia se reducen en un factor ~1000.

Nota: el solucionario mezcla cantidades. Con \(2^{31}\) modelos de \(2^8\) escenarios trabajan \(2^{39}\) hilos: \(t_s=5.12\cdot10^{-6}\cdot2^{39}\approx2.8\cdot10^6\) s, \(S=2^{39}\approx5.5\cdot10^{11}\) y, respecto a la capacidad de \(2^{41}\) hilos, \(E=2^{39}/2^{41}=0.25\). La idea a defender es la misma: 768 de cada 1024 hilos quedan ociosos.

Cómo resolverlo
  1. Restricción: un modelo (\(2^8\) escenarios) ocupa un bloque entero de \(2^{10}\) hilos → caben tantos modelos como bloques, \(2^{31}\).
  2. \(t_p\) no cambia (cada hilo sigue haciendo un escenario).
  3. Hilos que trabajan: \(2^{31}\cdot2^8=2^{39}\); la eficiencia frente a la capacidad es \(2^8/2^{10}=1/4\).
  4. Comenta: la restricción de memoria compartida desperdicia hilos; convendría empaquetar 4 modelos por bloque.

P2. Parallel stack (7 pts)

Bloque 2

Diseñe un stack paralelo donde los hilos almacenan o extraen información y además procesan información. Tiempo de cómputo no constante.

2.1 PRAM con: push de cualquier tamaño, pop, reconocer lleno/vacío y control de acceso en paralelo. (2 pts)

Resolución oficial
Input: n elementos, p hilos
for i = 1 to n pardo
    lock(); pop(); checkStackStatus(); unlock()
    run()            // Tcomp
    lock(); push(); checkStackStatus(); unlock()
Cómo resolverlo

Separa lo que toca la estructura compartida (siempre entre lock y unlock) de lo que es cómputo independiente (run, fuera del lock para que sea paralelo). Menciona que top es la variable compartida crítica y que check revisa top == -1 (vacío) o top == MAX-1 (lleno).

2.2 Describa el overhead. (1 pt)

Resolución oficial

\(T_p=n+p+T_{comp}(n)/p\): el almacenamiento es secuencial y el chequeo del stack es \(O(p)\). Overhead \(T_0=pT_p-W=np+p^2\).

Cómo resolverlo

Las regiones críticas se ejecutan de a una: los \(n\) accesos suman \(n\) aunque haya \(p\) hilos. Multiplica por \(p\) y resta \(W=T_{comp}\): queda \(np+p^2\).

2.3 ¿En qué casos (función de \(n\) y \(p\)) escala? (2 pts)

Resolución oficial

\(W=KT_0\Rightarrow T_{comp}(n)=K(pn+p^2)\). El término dominante es proporcional a \(np\), lo que lo hace difícilmente escalable.

Cómo resolverlo

Escala solo si el cómputo por elemento crece al menos como \(p\) (\(T_{comp}(n)/n\gtrsim Kp\)): tareas de grano grueso. Con tareas baratas, el stack serializado domina.

2.4 Directivas OMP necesarias (sin código compilable). (2 pts)

Resolución oficial

#pragma omp critical dentro de push, pop y checkStackStatus; en el main #pragma omp parallel shared(stack, top) con #pragma omp sections y una section por hilo que hace push/pop; omp_set_num_threads y omp_get_thread_num para identificar hilos.

Cómo resolverlo

Responde por función: qué protege cada directiva y por qué. Alternativas que suman: locks (omp_set_lock) para un stack específico, o critical(nombre) si hubiera varios stacks independientes.

P3. Floyd: filas vs bloques (7 pts)

Bloque 3

\(T_s=O(n^3)\). Filas: \(T_p=O(t_c\frac{n^3}{p}+\alpha n\log p+\beta n^2)\). Bloques: \(T_p=O(t_c\frac{n^3}{p}+\alpha n\log\sqrt p+\beta\frac{n^2}{\sqrt p})\).

3.1 Overhead e isoeficiencia en cada caso. (1 pt)

Resolución oficial

Filas: \(T_0=O(\alpha pn\log p+\beta pn^2)\). Bloques: \(T_0=O(\alpha pn\log\sqrt p+\beta p\frac{n^2}{\sqrt p})\).

Cómo resolverlo

Multiplica los términos de comunicación por \(p\). Recuerda \(p/\sqrt p=\sqrt p\), así que el último término de bloques es \(\beta\sqrt p\,n^2\).

3.2 Analíticamente, ¿cuál escala mejor? (1 pt)

Resolución oficial

Filas: \(n^3\propto pn^2\Rightarrow n\propto p\). Bloques: \(n^3\propto pn\log\sqrt p\Rightarrow n\propto\sqrt{p\log\sqrt p}\). Bloques escala mejor (menor dependencia de \(p\)).

Cómo resolverlo

Para bloques revisa ambos términos: \(\beta\) da \(n\propto\sqrt p\) y \(\alpha\) da \(n\propto\sqrt{p\log\sqrt p}\); manda el más restrictivo (\(\alpha\)). Aun así crece más lento que \(n\propto p\).

Resolución oficial

El cómputo domina sobre la comunicación y la eficiencia de ambos modelos se equipara (aunque sigue siendo mejor en bloques).

Cómo resolverlo

\(T_0/W\) cae como \(p/n\) (filas) o \(\sqrt p/n\) (bloques): ambos tienden a 0 cuando \(n\) crece, y \(E\to1\).

3.5 ¿Se cumple \(W=C_p\) (costo máximo) en algún modelo? (1 pt)

Resolución oficial

No, por el overhead.

Cómo resolverlo

\(C_p=pT_p=W+T_0\). Solo sería igual a \(W\) si \(T_0=0\), es decir, sin comunicación. Asintóticamente serían del mismo orden solo si \(T_0=O(W)\).

3.6 Si fuera \(W\propto p^3\), ¿qué consecuencia tendría? (1 pt)

Resolución oficial

Sería un modelo considerado altamente escalable (\(n\propto p\)).

Cómo resolverlo

Como \(W=n^3\), \(W\propto p^3\) equivale a \(n\propto p\): el tamaño lineal del problema crece igual que los procesos.

P1. KNN en GPU (6 pts)

Bloque 1

Tesla T4: \(2^{31}\) bloques, \(2^{10}\) hilos por bloque. Cada hilo calcula una distancia query-train: for j<d: diff = q[j]-t[j]; dist += diff*diff; (3 FLOP por dimensión).

1.1 Tamaño máximo de modelo por query (\(Q=1\)). ¿Qué problema observa? (1 pt)

Resolución oficial

\(2^{31}\cdot2^{10}=2^{41}\) datos de entrenamiento.

Cómo resolverlo

Un hilo por distancia, así que el máximo es el número total de hilos. Para el "problema": \(2^{41}\) puntos no caben en la memoria de la GPU (con \(d=64\) floats serían petabytes), y luego hay que ordenar \(2^{41}\) distancias para hallar los \(k\) vecinos.

1.2 \(N=10^5\), \(Q=10^4\), \(d=64\); un bloque por query. Carga por hilo. (1 pt)

Resolución oficial

Cada hilo resolvería ≈ 98 distancias.

Cómo resolverlo

Un bloque (1024 hilos) atiende las \(10^5\) distancias de su query: \(\lceil10^5/1024\rceil=98\). Se usan \(10^4\) bloques, muy por debajo de \(2^{31}\).

1.3 Tiempo paralelo con \(10^{-8}\) s por operación. (1 pt)

Resolución oficial

\(t_p=64\cdot3\cdot10^{-8}\cdot98=2\cdot10^{-4}\) s; \(t_s=2\cdot10^{-4}\cdot2^{10}\cdot10^4=2048\) s ≈ 34 min.

Cómo resolverlo

FLOP por distancia \(=3d=192\); por hilo \(192\cdot98\). Todos los bloques corren a la vez, así que ese es \(t_p\). Secuencial: \(t_p\) × hilos usados (\(2^{10}\cdot10^4\)).

1.4 Speedup, eficiencia y FLOP/s. (1.5 pts)

Resolución oficial

\(S=2048/2\cdot10^{-4}=10^7\); \(E=10^7/(2^{10}\cdot10^4)\approx1\); FLOP/s \(=64\cdot3\cdot98\cdot2^{10}\cdot10^4/2\cdot10^{-4}=9.6\cdot10^{14}\) ≈ 0.96 PFLOP/s. Misma justificación de proporcionalidad que en VaR.

Cómo resolverlo

El patrón se repite: \(S\) ≈ número de hilos usados y \(E\approx1\) porque no hay comunicación ni hilos ociosos (salvo los 352 que sobran en el último paso de cada bloque: \(98\cdot1024-10^5\)).

1.5 ¿Ventaja de asignar más de una query por bloque? (1.5 pts)

Resolución oficial

Aumentaría la carga por hilo. Como hay suficientes bloques, no habría ventaja.

Cómo resolverlo

Razona con recursos: sobran bloques (\(10^4\ll2^{31}\)), así que concentrar queries solo alarga \(t_p\). Ventaja posible que puedes mencionar: reutilizar en shared memory los datos de entrenamiento cargados para varias queries.

P2. Máximo en árbol k-ario, memoria distribuida (7 pts)

Bloque 2

Buscar el máximo de \(n\) elementos en un árbol k-ario (cada nodo con hasta \(k\) hijos) con \(p\) procesos en memoria distribuida.

2.1 PRAM y span. (1.5 pts)

Resolución oficial
for i = 0 to n-1 do B[i] = A[i]
m = n
while m > 1 do
    for i = 0 to ceil(m/k)-1 pardo
        j = i*k; localMax = B[j]
        for t = 1 to k-1 do
            if j+t < m and B[j+t] > localMax then localMax = B[j+t]
        B[i] = localMax
    m = ceil(m/k)
return B[0]

\(T_\infty=\log_k n\) (el while).

Cómo resolverlo

Generaliza la reducción binaria: en cada ronda los elementos se agrupan de a \(k\) y queda uno por grupo, así que \(m\) se divide entre \(k\). El número de rondas es \(\log_k n\). Cada ronda cuesta \(O(k)\) en rigor; el solucionario la toma como constante.

2.2 Complete el PRAM con el overhead distribuido y las directivas MPI. (1.5 pts)

Resolución oficial
MPI_Init; MPI_Comm_rank; MPI_Comm_size
local_n = n/p     // bloque local (p.ej. con MPI_Scatter)
local_max = max(local_A)                     // fase 1
step = 1
while step < p do                            // fase 2: reducción k-aria
    blockSize = step*k
    if rank mod blockSize == 0:              // padre
        for t = 1..k-1: child = rank + t*step
            if child < p: MPI_Recv(&r, ..., child); local_max = max(local_max, r)
    else if rank mod step == 0:              // hijo
        MPI_Send(&local_max, ..., rank - rank mod blockSize); break
    step = step*k
if rank == 0: imprimir local_max
MPI_Finalize
Cómo resolverlo

Tres fases: repartir (Scatter), cómputo local \(O(n/p)\), reducción entre procesos en un árbol k-ario de profundidad \(\log_k p\). La alternativa corta es MPI_Reduce(..., MPI_MAX, 0, ...), pero piden mostrar el árbol.

2.3 Complejidad \(T_p(n,p)\). (1 pt)

Resolución oficial

\(T_p(n,p)=O(\frac np+k\log_k p\,(\alpha+\beta))\).

Cómo resolverlo

En cada uno de los \(\log_k p\) niveles el padre recibe \(k-1\) mensajes de un dato (\(\alpha+\beta\) cada uno): \((k-1)\log_k p(\alpha+\beta)\approx k\log_k p(\alpha+\beta)\).

2.4 Escalabilidad. (1.5 pts)

Resolución oficial

\(T_0=O(n+kp\log_k p)\); \(W=K(n+kp\log_k p)\); \(n=K\,kp\log_k p\).

Cómo resolverlo

\(pT_p=n+kp\log_k p(\alpha+\beta)\), así que \(T_0=kp\log_k p(\alpha+\beta)\). Iguala \(W=n\) a \(K\) veces ese término: \(n=\Theta(kp\log_k p)\). Interpreta: casi lineal en \(p\), muy escalable.

2.5 Tiempo del mejor árbol k-ario (\(k\) óptimo). (1.5 pts)

Resolución oficial

Derivando \(T_p\) respecto a \(k\): \(T_p'=O(C\frac{\ln k-1}{\ln^2k})=0\) con \(C=\log_k p(\alpha+\beta)\), así que \(k=e\approx3\). \(T_{p,opt}=O(\frac np+e\log_k p(\alpha+\beta))\).

Cómo resolverlo
  1. Cambia de base: \(k\log_k p=\frac{k}{\ln k}\ln p\).
  2. Deriva \(f(k)=k/\ln k\): \(f'(k)=\frac{\ln k-1}{\ln^2k}\).
  3. \(f'(k)=0\Rightarrow\ln k=1\Rightarrow k=e\). Entero: \(k=3\).

Intuición: con \(k\) pequeño hay muchos niveles; con \(k\) grande cada padre recibe muchos mensajes.

P3. Matrices: filas vs bloques (7 pts)

Bloque 3

Filas: \(T=O(\frac{n^3}{p}+\alpha\log p+\beta n^2)\). Bloques: \(T=O(\frac{n^3}{p}+\alpha\sqrt p+\beta\frac{n^2}{\sqrt p})\).

3.1 Overhead e isoeficiencia. (1 pt)

Resolución oficial

\(T_{0,filas}=O(\alpha p\log p+\beta pn^2)\) (el solucionario escribe \(\alpha pn\log p\), es una errata); \(T_{0,bloques}=O(\alpha p\sqrt p+\beta p\frac{n^2}{\sqrt p})\).

Cómo resolverlo

Multiplica por \(p\) los dos términos de comunicación de cada modelo.

3.2 Analíticamente, ¿cuál escala mejor? (1 pt)

Resolución oficial

\(W_{filas}=n^3\propto pn^2\Rightarrow n\propto p\). \(W_{bloques}=n^3\propto p\sqrt p\Rightarrow n\propto\sqrt p\). Bloques escala mejor.

Cómo resolverlo

Bloques: el término \(\beta\sqrt p\,n^2\) da \(n\propto\sqrt p\) y el \(\alpha p^{3/2}\) también (\(n^3\propto p^{3/2}\)). Filas: \(\beta pn^2\Rightarrow n\propto p\), que es más restrictivo.

Resolución

El solucionario repite la tabla de Floyd de la Sección 1 (dice "N=10⁴"), que no corresponde a estos datos. Estos son los valores correctos con \(E=n^3/(n^3+T_0)\):

3.4 ¿Se cumple \(W=C_p\)? (1 pt)

Resolución oficial

No, por el overhead.

Cómo resolverlo

\(C_p=W+T_0\) con \(T_0>0\) en ambos modelos.

3.5 ¿Se cumple \(W\propto p^3\)? ¿Consecuencias? (1 pt)

Resolución oficial

Según 3.2 no se da \(n^3\propto p^3\). Sería un modelo altamente escalable (\(n\propto p\)).

Cómo resolverlo

Ojo: en filas sí sale \(n\propto p\), es decir \(W\propto p^3\). Puedes señalarlo con la misma lectura del solucionario de Floyd: crecimiento lineal de \(n\) con \(p\). Lo importante es explicar qué significa \(n\propto p\) frente a \(n\propto\sqrt p\).

3.6 Granularidad de cada modelo y efecto en la escalabilidad. (1.5 pts)

Resolución oficial

\(G_{filas}=\dfrac{n^3/p}{\alpha\log p+\beta n^2}\), \(G_{bloques}=\dfrac{n^3/p}{\alpha\sqrt p+\beta n^2/\sqrt p}\). Bloques tiene mayor granularidad, optimizando el particionamiento del dominio.

Cómo resolverlo

\(G=T_{comp}/T_{comm}\). El denominador de bloques tiene \(n^2/\sqrt p\) en vez de \(n^2\): más cómputo por unidad de comunicación ⇒ \(E=G/(1+G)\) más alta y mejor escalabilidad.

P1. Detección de incendios en GPU (6 pts)

Bloque 1

H100 (\(2^{10}\) hilos por bloque, \(2^{31}\) bloques). Imagen \(N\times N\), \(N=8192\), tres bandas por píxel. Un hilo por píxel:

ndvi = (nir-rojo)/(nir+rojo+1e-6)
riesgo = 0
for m in 0..499:
    r = 0.7*temp + 0.3*(1-ndvi)
    for q in 0..99:
        r = 0.6*r + 0.4*sinf(r)
    riesgo += r
riesgo /= 500;  clase = (riesgo>=0.8)?2:(riesgo>=0.5)?1:0

1.1 FLOP por hilo (sinf = 40 FLOP). ¿Es adecuado o conviene repartir el píxel entre varios hilos? (1.5 pts)

Resolución oficial

\(W_{pixel}=500(4+100\cdot43+1)=2\,152\,500\approx2\) MFLOP. Hay paralelismo masivo y granularidad suficiente, pero 2 MFLOP por hilo puede ser mucho; se puede repartir el kernel entre varios hilos. Obliga a sincronizar, pero ese overhead es menor que el cómputo.

Cómo resolverlo
  1. Bucle interno: \(0.6r\) (1) + \(0.4\sin r\) (1 + 40) + suma (1) = 43 FLOP, × 100.
  2. Cuerpo del externo: \(0.7T+0.3(1-\text{ndvi})\) = 4 FLOP, + \(\text{riesgo}\mathrel{+}=r\) = 1.
  3. × 500. Lo de fuera de los bucles (ndvi, división) es despreciable.

1.2 Aplique Foster (GPU). (1 pt)

Resolución oficial

Partición: cada píxel es independiente: \(8192^2=67\,108\,864\) tareas. Comunicación: no hay comunicación explícita entre tareas; solo con memoria global y CPU–GPU. Aglomeración: bloques de hilos, por ejemplo 256. Mapeo: 256 hilos por bloque; los bloques se asignan a los SM.

Cómo resolverlo

Responde los cuatro pasos con un número concreto en cada uno. Justifica 256: múltiplo del warp (32), buena ocupación de los SM, accesos coalescentes.

1.3 Configuración óptima de bloques e hilos; hilos inactivos por if(idx<P). (1.5 pts)

Resolución oficial

\(G=P/B=67\,108\,864/256=262\,144\) bloques; \(262\,144\cdot256=67\,108\,864\) hilos ⇒ 0 inactivos. La condición es necesaria en el caso general, cuando \(P\) no es múltiplo de \(B\).

Cómo resolverlo

\(P=2^{26}\), \(B=2^8\Rightarrow G=2^{18}\). Inactivos \(=G\cdot B-P\). Con \(B=1024\) también sería exacto (\(2^{16}\) bloques).

1.4 Tiempos secuencial y paralelo. (1 pt)

Resolución oficial

Con \(10^{-8}\) s por operación: \(T_p=2\,152\,500\cdot10^{-8}=0.02\) s; \(T_s=T_p\cdot67\,108\,864=1\,444\,518\) s ≈ 17 días.

Cómo resolverlo

Mismo patrón que siempre: \(T_p\) = FLOP de un hilo × \(t_{op}\); \(T_s\) = \(T_p\) × número de píxeles.

1.5 Speedup y eficiencia respecto al pico (1 GFLOP/s): \(E_{GPU}=\) velocidad alcanzada / pico. (1 pt)

Resolución oficial

\(S=T_s/T_p\approx67\,108\,863\). Velocidad alcanzada \(=\text{FLOP}/T_p\approx0.1\) GFLOP/s; \(E_{GPU}=0.1/1=0.1\).

Cómo resolverlo

\(2.15\cdot10^6\) FLOP en \(0.0215\) s = \(10^8\) FLOP/s por hilo. Interpreta: se usa el 10 % del pico, porque el tiempo por operación dado (\(10^{-8}\) s) equivale a 0.1 GFLOP/s.

P2. Isoeficiencia en memoria compartida, distribuida e híbrida (7 pts)

Bloque 3

Malla \(n\times n\), \(k\) iteraciones, \(W=kn^2\), \(b\) bytes por elemento, memoria por nodo \(M_{nodo}\). Compartida (\(P\) núcleos): \(T_P=\frac{kn^2}{P}+k\gamma\log P\). Distribuida (\(P\) procesos): \(T_P=\frac{kn^2}{P}+k\alpha\log P+k\beta n\log P\).

2.1 Tiempo híbrido con \(q\) nodos de \(m\) hilos (\(P=qm\)). (1 pt)

Resolución oficial

\(T_P^{(H)}=\frac{kn^2}{P}+k\gamma\log m+k\alpha\log q+k\beta n\log q\).

Cómo resolverlo

El cómputo se reparte entre todos los núcleos (\(P\)). La sincronización de memoria compartida ocurre dentro del nodo (\(m\) hilos → \(\log m\)); la comunicación MPI ocurre entre nodos (\(q\) → \(\log q\)).

2.2 Overhead e isoeficiencia de cada paradigma. (2 pts)

Resolución oficial

Compartida: \(T_0=kP\gamma\log P\Rightarrow n^2=\Theta(P\log P)\Rightarrow W_{MC}=\Theta(kP\log P)\).

Distribuida: \(T_0=kP\alpha\log P+kP\beta n\log P\). Latencia: \(n^2=\Theta(P\log P)\). Comunicación: \(n^2=\Theta(Pn\log P)\Rightarrow n=\Theta(P\log P)\Rightarrow W_{MD}=\Theta(kP^2\log^2P)\).

Híbrida: \(T_0=kP\gamma\log m+kP\alpha\log\frac Pm+kP\beta n\log\frac Pm\). Dominante: \(W_H=\Theta(kP^2\log^2\frac Pm)\).

Cómo resolverlo

Para cada paradigma: \(T_0=PT_P-kn^2\); luego \(kn^2=K\cdot\)(cada término). El truco está en el término \(\beta n\log P\): como contiene \(n\), al despejar queda \(n\propto P\log P\) y \(W=kn^2\propto kP^2\log^2P\). Escribe siempre los tres términos y marca el dominante.

2.3 ¿Qué paradigma escala mejor? (1 pt)

Resolución oficial

Para \(1<m<P\): \(kP\log P<kP^2\log^2\frac Pm<kP^2\log^2P\). Compartida tiene la mejor isoeficiencia, distribuida la peor y la híbrida queda entre ambas.

Cómo resolverlo

Ordena las tres funciones por crecimiento. La híbrida mejora a la distribuida porque la comunicación cara solo ocurre entre \(q=P/m\) nodos.

2.4 Restricción de memoria (compartida: todo en una máquina; distribuida: \(P\) nodos). (1.5 pts)

Resolución oficial

Compartida: \(bn^2\le M_{nodo}\Rightarrow W\le k\frac{M_{nodo}}{b}\); viable solo si \(CP\log P\le kM_{nodo}/b\). Distribuida: \(bn^2\le PM_{nodo}\Rightarrow W\le kP\frac{M_{nodo}}{b}\). Híbrida: \(q=P/m\) nodos ⇒ \(W\le k\frac{PM_{nodo}}{mb}\).

Cómo resolverlo

Memoria total disponible × \(1/b\) = elementos que caben = \(n^2\) máximo. Multiplica por \(k\) para pasar a \(W\). Luego cruza con la isoeficiencia: la compartida necesita que \(W\) crezca como \(P\log P\), pero tiene un techo fijo.

2.5 Considerando isoeficiencia y memoria, ¿qué paradigma conviene en la práctica? (1.5 pts)

Resolución oficial

Compartida escala mejor en eficiencia pero peor en capacidad (no resuelve problemas arbitrariamente grandes). Distribuida escala mejor en memoria pero peor en eficiencia. La híbrida equilibra eficiencia y capacidad.

Cómo resolverlo

Responde con el trade-off explícito y una recomendación: híbrida (MPI entre nodos + OpenMP dentro), que es lo que se usa en supercomputadores.

P3. DTS vs PWS (7 pts)

Bloque 2

Árbol con ramificación \(b\) y profundidad \(d\), \(W=T_s=b^d\). DTS: genera la frontera a profundidad \(r=d/2\) (\(|S|=b^r\) subárboles balanceados), explora cada subárbol en paralelo con DFS y reduce. PWS: \(q=p\) ventanas de costo; cada una explora desde la raíz con trabajo redundante \(O(W^{2/3})\).

3.1 Trabajo y span de DTS. (1.5 pts)

Resolución oficial

\(T_1=W=b^d\). Frontera \(\Theta(b^r)\), subárbol \(\Theta(b^{d-r})\), reducción \(\Theta(r\log b)\). \(T_\infty=\Theta(b^r+b^{d-r})\); con \(r=d/2\): \(T_\infty=\Theta(b^{d/2})=\Theta(W^{1/2})\).

Cómo resolverlo

El span es la suma de las fases en secuencia: generar frontera, luego el subárbol más largo, luego reducir. El logaritmo es despreciable frente a las exponenciales. Usa \(b^{d/2}=\sqrt{b^d}=\sqrt W\).

3.2 \(T_p\) de DTS. (0.5 pts)

Resolución oficial

Brent: \(T_p^{DTS}=O(\frac Wp+W^{1/2})\).

Cómo resolverlo

Sustituye en \(T_p=T_1/p+T_\infty\).

3.3 Isoeficiencia de DTS. (1 pt)

Resolución oficial

\(T_0=pc_1W^{1/2}\). \(W=Kpc_1W^{1/2}\Rightarrow W^{1/2}=Kpc_1\Rightarrow W=K^2c_1^2p^2\Rightarrow W_{DTS}=\Theta(p^2)\).

Cómo resolverlo

Cuando \(W\) aparece en ambos lados, divide entre la potencia de \(W\) del lado derecho y eleva para despejar.

3.4 Trabajo y span de PWS. (1.5 pts)

Resolución oficial

Tarea más pesada: \(\Theta(\frac Wq+W^{2/3})\) con \(q=p\); reducción \(\Theta(\log p)\). \(T_\infty^{PWS}=\Theta(\frac Wp+W^{2/3})\). Trabajo total \(T_1^{PWS}=\Theta(W+pW^{2/3})\); para la eficiencia se toma como base \(W=b^d\).

Cómo resolverlo

Cada ventana hace su parte ideal más la parte redundante. El span es la ventana más lenta. El trabajo total suma \(p\) veces la redundancia, pero la eficiencia se mide contra el mejor secuencial (\(b^d\)).

3.5 \(T_p\) de PWS. (0.5 pts)

Resolución oficial

\(T_p^{PWS}=O(\frac{W+pW^{2/3}}{p}+\frac Wp+W^{2/3})=O(\frac Wp+W^{2/3})\).

Cómo resolverlo

Brent con el trabajo total; los términos repetidos se absorben en la \(O\).

3.6 Isoeficiencia de PWS. (1 pt)

Resolución oficial

\(T_0=pc_2W^{2/3}\). \(W=Kpc_2W^{2/3}\Rightarrow W^{1/3}=Kpc_2\Rightarrow W=K^3c_2^3p^3\Rightarrow W_{PWS}=\Theta(p^3)\).

Cómo resolverlo

Igual que en DTS: divide entre \(W^{2/3}\) y eleva al cubo.

3.7 ¿Qué método escala mejor? (1 pt)

Resolución oficial

\(W_{DTS}=\Theta(p^2)\ll W_{PWS}=\Theta(p^3)\): DTS requiere un crecimiento menor del problema para mantener la eficiencia. DTS escala mejor.

Cómo resolverlo

Compara exponentes y conecta con la causa: el trabajo redundante de PWS (\(W^{2/3}\)) es mayor que el span de DTS (\(W^{1/2}\)), porque la heurística no separa bien las ventanas.
